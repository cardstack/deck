The Deckbook

Deck is a protocol for versioning, publishing, and serving ES modules and JSON from plain state — a directory tree, an import map, seals, and immutable version pointers. This book teaches the running reference implementation: CLI, store, server, history, and the workflows they unlock.

Reference impl built Tier‑1 store always on Tier‑2 history optional No framework required

1. The promise

No npm. No GitHub. No deploy. No PR — for the loop that matters while you are building. Edit a file, see it live, keep every settled state, ship a name when you mean it, share a zip anyone can open, pull any ESM library in-house, fork without consequences.

PromiseMechanism (implemented)
Instant feedbackVersion-less URL → working tree, Cache-Control: no-store
Never lose workAuto-publish <base>-dev.N + optional per-save seals
Revert anytimedeck unpack a pack, or deck restore <changeId> (tier 2)
Ship any versiondeck release --from dev — pointer, zero bytes copied
Share a milestonedeck pack → .pack.zip (standard zip)
Use any librarydeck vendor hermetic CDN graph → your store
Fork freelydeck fork into your publisher scope
Stability on demanddeck lock turns ranges into exact pins
Whole web platformPlain ESM + import maps; no bundler required

3. The layout is the address

What ls shows and what the URL says are the same shape. A depot carries its machinery inside itself — .deck/store/ for sealed versions, .jj/ for seals — both invisible to the tree hash, so copying the directory takes live files, published versions, and history with it. 

<root>/site/acme/palette/palette.js     on disk
       /site/acme/palette/palette.js    live — every save, no-store
       /site/acme/palette@1.1.0/palette.js
                                        sealed copy, immutable forever
       /site/_history/<changeId>/acme/palette/palette.js
                                        any state it was ever in (tier 2)
Publisher segment = fork boundary. acme/palette and you/palette are different decks with different version lines in the same depot. Undiverged forks cost no extra pack bytes — the store is content-addressed.

4. Three levels of volatility

All just import-map values / URL forms. Opting into churn is always explicit.

You wantYou writeYou get
Every save, instantly"live" / version-less URLWorking tree, no-store
Freshest auto-seal"dev" or @devShort-TTL redirect to newest -dev.N
Something dependable"^1.0.0" / exactStable resolution; ranges ignore prereleases

latest is a dist-tag on a stable release. latest is not live — live is the bytes on disk with no version segment.

5. The live loop

The core vibe-coding workflow, as implemented:

deck hello ./work          # scaffold + serve (or: deck serve --root ./work)
# edit anything under a deck directory
# → debounce (~500ms quiet)
# → treeHash unchanged? stop
# → packFromDir → publish <base>-dev.N, tag:dev
# → [tier 2] history backend seals the save too

deck release --depot ./work/site --publisher acme --name palette \
  --version 1.1.0 --from dev --tag latest

HMR-lite

/_live/events (SSE) + drop-in /_live/hmr.js reloads pages that depend on changed live decks.

Import-map injection

HTML responses get a real inline import map (browsers ignore external map scripts). Sealed pack bytes stay untouched.

6. Store & packs

At rest, each package lives under the depot store:

<depot>/.deck/store/<publisher>/<name>/
  meta.json                          # versions + dist-tags (pointers)
  packs/<treeHash>.pack.zip          # bytes once per content hash
  • Publish verifies a pack, writes bytes only if the treeHash is new, then adds a version pointer.
  • Release names an existing sealed state — never copies bytes.
  • Prune drops old -dev.N records; deletes pack files only when nothing still points at them.
  • Pack laws: treeHash survives pack→unpack; pack∘unpack is byte-identical for canonical packs; stock unzip works.

7. History tiers (be honest)

TierWhat you getStatus
1 — store only Every settled save → immutable -dev.N pack. Restore by unpacking. No seals between publishes. Always on
2 — jj / historyd Every save sealed; /<depot>/_history/<changeId>/…; deck history / deck restore; packlist can name sealChangeId. Implemented when --history auto|jj|historyd attaches
Capability is reported, not pretended. GET /_packages includes a history block (tier, jj, historyd). Missing jj or a dead daemon degrades to tier 1 with a printed reason — the live/auto-publish loop keeps working. 
deck serve --root ./work --history auto
deck history ./work/site
deck restore ./work/site <changeId>   # leaves current state sealed first

8. Safe vendor — your own unpkg

Pull a CDN module graph once, rewrite references to stay inside the pack, seal it. Runtime imports hit your Deck server only. Hermetic by default; --allow-external / --allow-host are explicit opt-outs. Identity travels as vendoredFrom. 

deck vendor https://esm.sh/simplex-noise@4.0.1 \
  --name simplex-noise --version 4.0.1 \
  --depot ./work/site --publisher acme --tag latest
<script type="importmap">
{ "imports": { "simplex-noise": "/site/acme/simplex-noise@4.0.1" } }
</script>

9. Fork, lock, offers, rebase

Contribution is a version you can run, not a diff waiting for merge theater.

Fork

deck fork --depot ./work/site \
  --from acme/palette --as you/palette --use-in you/app

Copies into your publisher scope; optional --use-in repoints a consumer at the fork live. Records base (package, version, treeHash) so the fork is an offer.

Lock

deck lock --depot ./work/site --publisher you --name app
deck lock --depot ./work/site --publisher you --name app --check

Resolves declared ranges to exact pins in the import map — users never inherit someone else's working tree.

Try by URL

/site/you/app/index.html?with=acme/palette=you/palette
/site/you/app/index.html?with=acme/palette@1.1.0

Server rewrites resolution for that request only. No checkout, no build, not cached as sealed content.

Offers & rebase

deck offers --depot ./work/site
deck rebase --depot ./work/site          # or: deck serve --rebase
GET /site/_offers
  • Clean merges write into the proposal tree (auto-publish + seal).
  • Conflicts are reported and left untouched — machines never damage contributor work.
  • JSON merges as data (key-level), not as lines — so adding adjacent keys is not a fake conflict.
  • Accepting a proposal is a pointer move to a treeHash already held. Zero bytes copied.

12. Use cases, at the command line

From docs/deck-use-cases.md — shapes of work that need this, not merely benefit. Below, each one is worked as a sequence of real commands. Every transcript on this page was captured from an actual run against this implementation; nothing is illustrative.

One local depot. Libraries come from npm, vendored in. There is no remote Deck in any of these. A Deck server runs on your machine, owns your files, watches them, serves your app, and seals every save. Third-party code is pulled from npm or a CDN once, sealed into your own store, and served from your own server from then on. Nothing your app loads at runtime comes from a host you do not control.

12.0 The setup all four share

A depot is a directory of decks. Make two — a component and an app that uses it — and serve the lot: 

work/tool/ui/table/        importmap.json  table.js
work/tool/app/dashboard/   importmap.json  app.js  index.html
deck serve --root ./work --history auto
  tool: history: jj 0.43.0 (seal-grained)
  watching tool/app/dashboard
  watching tool/ui/table
deck server on http://localhost:8788 (read-only)
  browse: http://localhost:8788/  — depots, packages, versions
  hmr:  http://localhost:8788/_live/hmr.js → SSE /_live/events
  live: http://localhost:8788/tool/ui/table/ — auto-publishes @<base>-dev.N (tag: dev)
  seals: http://localhost:8788/tool/_history — every save, published or not
auto-published tool/ui/table@0.1.0-dev.1 (d42dbe7c47d5) sealed pwwxoqtvxssy

That last line is the whole loop, and it happened without you asking. Now edit table.js and save it — twice: 

auto-published tool/ui/table@0.1.0-dev.2 (9f4f2d43a2d2) sealed wtmrttzrvvwp
auto-published tool/ui/table@0.1.0-dev.3 (b90501707b14) sealed zkzwlotsqyzm

Each save is debounced (~500ms of quiet), hashed, and — only if the tree hash changed — published as an immutable version and sealed. Touching a file publishes nothing. Two identifiers appear on every line and they are different things: the tree hash is what the bytes are, and the changeId is which save it was. 

deck history ./work/tool --limit 3
zkzwlotsqyzm  2026-08-08T19:59:32-0400  save: ui/table/table.js
              M ui/table/table.js
wtmrttzrvvwp  2026-08-08T19:59:29-0400  save: ui/table/table.js
              M ui/table/table.js
pwwxoqtvxssy  2026-08-08T19:59:27-0400  save
              A app/dashboard/app.js
              A ui/table/table.js

Meanwhile the version-less URL is the working tree, and says so in a header the browser is obliged to honour: 

curl -si http://localhost:8788/tool/ui/table/table.js
HTTP/1.1 200 OK
content-type: text/javascript; charset=utf-8
cache-control: no-store
repr-digest: sha-256=:LCVAhA3V5YjeY287uQSy1dLTffMDbV7pvtIxdhQlxNA=:
x-deck-depot: tool
Without jj the first line reads tier 1 instead, and everything else here still works. You keep every settled save as an immutable version; what you lose is the saves between publishes, and with them deck history and deck restore.

12.1 The swarm-built internal tool

Eight agents, one component each, one human steering. The app composes them through its import map, so the assembled thing exists continuously — there is no integration step, because there was never a disintegration.

Declare what the app uses, at the volatility you want

The key is the import specifier your source already writes. The value is how much churn you are opting into, chosen per component: 

{
  "deck": {
    "dependencies": {
      "ui/table":       "live",      // you are editing this one
      "ui/filter-bar":  "live",
      "charts/revenue": "dev",       // freshest seal, someone else's
      "charts/funnel":  "^1.2.0",    // chart 3 went bad — frozen
      "data/warehouse": "^2.0.0"     // must not move under you
    }
  }
}

Resolve the ranges into pins

deck lock --depot ./work/tool --publisher app --name dashboard
ui/table  live → /tool/ui/table/table.js
nanoid  lib/nanoid@^5.0.0 → /tool/lib/nanoid@5.0.9/index.browser.js
locked app/dashboard

The pins are written into importmap.json, so cat is how you read the lock, the lock travels inside the pack, and moving a dependency forward is an ordinary save that auto-publishes and seals like any other.

Quarantine one agent without stopping the others

Chart 3 is producing nonsense. Change one line from live to ^1.2.0 and re-lock. That panel freezes at its last good release; the other seven keep moving under you. No branch, no revert, no conversation.

Check the pins are not lying

deck verify-links --depot ./work/tool --publisher app --name dashboard
  ok  app/dashboard  3 link(s)
1 deck(s) verified

Offline, on purpose. It checks that every pin resolves to what its dependency record implies, that every pin has a record and every record a pin, and that the files named actually exist. deck lock --check runs the same gate and refuses to write — that is the CI shape.

12.2 Codelists and reference data

A shared table of facts — currencies, tax rates, a model-and-pricing registry — amended constantly by whoever noticed a fact was wrong. This is the worst case for git+npm and the best case for Deck.

Ship a release — and meet the one gate that is not obvious

A version is a pointer, so releasing copies nothing. But the sealed manifest has to agree that it is the version being released: 

deck release --depot ./work/tool --publisher ui --name table --version 1.0.0 --from dev
error: importmap.json declares ui/table@0.1.0, but the request is publishing ui/table@1.0.0

So bump deck.packages.<name>.version to 1.0.0. That is an ordinary save, which means the watcher publishes and seals it for you: 

auto-published tool/ui/table@1.0.0-dev.1 (9c1fb4417167) sealed kppyzoyuwutt
deck release --depot ./work/tool --publisher ui --name table \
  --version 1.0.0 --from dev --tag latest
released ui/table@1.0.0 from dev: same sealed state (treeHash 9c1fb4417167c9ee…), zero bytes copied, tag latest

An amendment publishes to the dev line the instant it is saved, and no ^1.0.0 consumer sees it — ranges never match prereleases. A curator names a batch when it is right, and that naming is instant no matter how large the list.

Keep your patched copy, and stay current anyway

Your fork has three internal currency codes in it. A fork records its base, so it is a proposal — nothing registers it: 

deck fork --depot ./work/tool --from ui/table@1.0.0 --as you/table --use-in app/dashboard
forked ui/table@1.0.0 → you/table (2 files) at …/work/tool/you/table
  it publishes under you/table; ui/table's versions never move
  app/dashboard now gets you/table live wherever it imports ui/table — every save, no publish
deck offers --depot ./work/tool
current      you/table ← ui/table@1.0.0
1 open, 0 need a person

Nobody rebases

Upstream releases 1.1.0. The base is exact and both sides are content-addressed, so re-merging is a pure function a machine runs: 

deck rebase --depot ./work/tool
rebased      you/table ← ui/table@1.1.0  (written)
1 rebased, 0 need a person

The merge landed in the fork's own tree — which auto-published and sealed like any other save — and the base pointer moved to what it absorbed. JSON merges by key, not by line, so two people adding two different currency codes both land and neither is a conflict.

What happens when it really is a conflict

Both sides change the same key differently. The machine reports it and writes nothing — not even the part that merged: 

conflicted   you/table ← ui/table@1.2.0  conflicts: table.js
0 rebased, 1 need a person

fork tree before: tree-hash-v1:58519146809b424024290db3579bd1e4b9d860353c099c4d96026f12d710d7d3
fork tree after:  tree-hash-v1:58519146809b424024290db3579bd1e4b9d860353c099c4d96026f12d710d7d3

Byte-identical. A machine never damages a contributor's work. Run it continuously with deck serve --rebase, and a maintainer with 200 open proposals sees the three that stopped merging rather than the 197 that someone should rebase.

12.3 Adapters, patterns, and the automation you wrote for yourself

"Slack → Google Doc" is four things with different physics: a stable adapter, your bespoke pattern, the generic pattern it could become, and an instance that is pure config. Today each is exiled to a different system, so the promotion from bespoke to generic is a rewrite and mostly nobody does it.

Bring the adapter in-house, once

deck vendor npm:nanoid@5.0.9 --depot ./work/tool --publisher lib --tag latest
vendored 2 modules from nanoid@5.0.9 (entry index.browser.js, 0 rewritten — byte-identical to what npm published)
  treeHash 81c7824d64e5070895728b60233e96466afdad649d188fe225df0210f76cad36
published lib/nanoid@5.0.9 tag latest — import it as /tool/lib/nanoid@5.0.9/

For something with dependencies of its own, deck vendor-tree does the whole graph — one deck per package, wired by aliased dependency records — so a library two of your decks share is stored and loaded once. A version published in the last 30 days is refused by default; that is the shape most supply-chain attacks arrive in.

Promote bespoke → generic without migrating anything

deck fork --depot ./hub --from me/ship-notes --as team/message-to-doc

Pull the hardcoded IDs out into config.schema.json and release 1.0.0. Your private one keeps working, untouched, pinned to whatever it was pinned to. The generic one has its own version line from birth. Nothing migrated, and the extraction pays twice: a pattern that declares a config schema is configurable without any UI work, and an instance is a JSON document validated against it.

Three strata, three volatilities, one address space

"lib/slack":          "^2.0.0"    // adapter — changes when Slack changes
"team/message-to-doc": "dev"      // pattern — weekly
"me/ship-notes":      "live"      // instance — whenever you tweak it

12.4 Skills and agent capabilities

A skill is a deck of markdown and JSON. Prompt work is the highest-frequency, lowest-ceremony editing there is — a good skill is 200 tiny edits — and the only real evaluation is running the harness.

Keep all 200 iterations without authoring a single commit message

Nothing to do. The watcher already sealed every one of them, and published the ones that changed the tree.

A/B two skills by opening two links

curl -si "http://localhost:8788/tool/app/dashboard/index.html?with=ui/table=you/table"
HTTP/1.1 200 OK
cache-control: no-store
x-deck-importmap: injected
x-deck-with: ui/table, ui/table/

The server resolved that one request's import map differently, using the same rules deck lock uses. No checkout, no build, no branch, and the app's own tree is untouched. Repeat with to swap several at once. A trial is no-store and carries x-deck-with, so it can never be cached as if it were the sealed thing.

Decide the version from 40 minutes ago was better

restored ./work/tool to zkzwlotsqyzm…: 2 file(s) written, 0 removed
  app/dashboard/importmap.json

The hour you are abandoning was sealed before the restore ran, so this is undoable. Nothing is rewound: a restore replays forward as ordinary writes, which auto-publish as the next dev version. History only grows.

13. Coding on Deck

The four workloads above are shapes of software. This one is the act of writing it — vibe coding with agents, and using Deck as the revision system while you do. It is the workload every other workload sits inside, and the one where the protocol's odder decisions stop looking odd.

Deck as your revision system

Not a replacement for git in general — a replacement for what git is doing on the twenty tabs of half-finished work you have open right now. Those two jobs have almost nothing in common, and git is only good at one.

You wantgitDeck
keep this state add, commit -m "…", think of a message save the file. It is sealed and, if the tree changed, published
see it running build, serve, reload it is already at a URL, no-store, this instant
go back an hour reflog, reset, hope deck restore <changeId> — and that is itself undoable
two things at once two branches, one worktree, or a stash two decks. There was never one tree to share
ship it tag, build, publish, wait release --from dev — a pointer, zero bytes
someone else's change a diff to read a URL to run

The load-bearing difference is ceremony per state. Git charges you a commit message for every state you want to keep, so you keep the states you can name — and the ones worth going back to are almost never those. They are the accidental ones: the version from forty minutes ago, before the refactor that seemed obviously right. Deck charges nothing, so it keeps them all.

Going back always goes forward. deck restore seals the state you are leaving first, then writes the old one as ordinary saves, which auto-publish as the next dev version. Nothing is rewound and nothing is rewritten. That is why there is no reset in this CLI and no --force anywhere near history: an operation that can destroy work is a bad operation to have available at 2am.

Two agents at once

The thing that actually breaks when you point several agents at one codebase is not merge quality. It is that they share a working tree, so one of them is always waiting or clobbering. Deck's answer is structural: one deck per component, so there is nothing to share. 

auto-published tool/ui/table@0.1.0-dev.1 (a4e81bdb2b71) sealed zyrspmpksmzk
auto-published tool/charts/spark@0.1.0-dev.1 (7cfa1b609b9c) sealed zyrspmpksmzk
two saves, two version lines, zero merges — different decks.

Both saves landed inside one seal window, so they share a changeId and still have separate version lines. Nobody waited, and no merge ran, because a merge only exists where two writers touched one name.

They eventually will. When both amend the same shared deck — a token set, a codelist — the three-way merge runs against the base each fork recorded, and most of the time there is nothing to argue about: 

agent-a/tokens   rebased      1.1.0  (written)
agent-b/tokens   rebased      1.1.0  (written)
agent-a: ink, surface, muted, accent
agent-b: ink, surface, muted, warning

Three different keys under one JSON object. Both forks absorbed upstream's and kept their own. Nobody reviewed anything, because a line merge's idea of "adjacent lines changed" was never a real disagreement.

The conflict that is real, and resolving it deterministically

Then they collide for real: the same key, two answers. The generic merge refuses — and refuses completely: 

agent-a/tokens   conflicted   1.2.0  ← tokens.json
agent-a's tree: 66febf4edc8b… before, 66febf4edc8b… after — byte for byte

It has to refuse, because it does not know what the key means. scale is a set, so two people extending it are agreeing. radius is a scalar, so two people setting it are disagreeing — but there may still be a house rule. Nothing generic can tell those apart, and a merge tool that guessed would be worse than one that stops.

So the rules are published data, in upstream's own sealed tree, versioned like everything else: 

// std/tokens/merge-policy.json
{ "rules": { "scale": "union", "radius": "max" } }

A resolver reads them and settles what they cover: 

radius   base 4  upstream 8  fork 12
         → rule "max" → 12
scale    base [4,8,16,24]  upstream [4,8,16,24,40]  fork [4,8,16,24,48]
         → rule "union" → [4,8,16,24,40,48]
both intentions survived: 48 is agent-a's, 40 is upstream's.

Three properties make that a resolution rather than a coin flip.

  • Deterministic. Every rule is a pure function of (base, upstream, fork). union sorts, so it does not matter which side is called ours; the demo asserts that two dry runs agree and that the commutative rules actually commute.
  • Auditable. The rule that decided each key is reported, and it came from a file anyone can read at an immutable URL. Upstream owns the rules, so a proposal cannot grant itself the right to win.
  • Fail-closed. A key with no rule is not guessed. The whole resolution is abandoned and nothing is written — not even the keys it could have settled. 
REFUSED  tokens.json name: no rule declared
nothing written. One person decides one key, instead of three.

That last line is the point of the whole arrangement. Unattended merging is only safe if its refusals are trustworthy, and a resolver that quietly picks a side is worse than none — you stop reading its output, and then you stop noticing what it decided for you.

Runnable: pnpm --filter @deck/example-two-agents demo, or the two-agents panel in the hub. It is also the demo that turns tier-2 history on, so every save there has a changeId and not just every publish.

A, B or C — choosing between an agent's variations

Ask for three ways to do something and you get three answers at three different layers. They are not drafts of one edit; they have different blast radii, so a person has to choose:

layerthe editchanges
Adatashrink the spacing scaleevery deck that reads the tokens
Bviewa compact cardevery page that renders a card
Ccompositionmore columnsthis page only

Each is published the moment it exists, and publishing moves nothing:

A  data         std/tokens@1.1.0-try.a   53e94c367a70…
B  view         ui/card@1.1.0-try.b      addbe50dc750…
C  composition  app/gallery@1.1.0-try.c  29fd5d6d8f8d…
latest still points at 1.0.0 for all three. Ranges never match prereleases.

Review is four iframes of one sealed page, each asked for with a different ?with=. No checkout, no build, no branch, and the app's own tree is identical in all four. 

/site/app/preview/preview.html?with=std/tokens@1.1.0-try.a&with=ui/card@1.0.0&with=app/gallery@1.0.0

Choosing is a tag move:

deck release --depot ./depot --publisher ui --name card \
  --version 1.1.0 --from try-b --tag latest
ui/card@1.1.0 ← 1.1.0-try.b
same tree addbe50dc750…, same stored object, zero bytes copied

And the two you rejected are not deleted, not stashed, and not on a branch. They are published versions with no latest pointing at them, which is all "not latest" has ever needed to mean: 

A  std/tokens@1.1.0-try.a   tags: try-a   1078 bytes, still rebuilds
C  app/gallery@1.1.0-try.c  tags: try-c   1305 bytes, still rebuilds

Change your mind in a month and it is the same pointer move again. This is the part that has no equivalent anywhere else: rejected work normally either pollutes the branch list until someone prunes it, or evaporates when the agent's context window closes.

Runnable: pnpm --filter @deck/example-variations demo, or CHOOSE=a / CHOOSE=c to promote a different one.
